## 14. 本轮追加（同一份交接、同一天的第二段会话）：`<ERR BASE.n>` 的根因

**一句话**：那个号不是消息 id，是**我们自己 PC 菜单里一个字符串缓冲的地址**。wasm 上
`isGameTextPointer()` 只认游戏堆里的指针，模块静态区不算，于是字符串走了"消息 id"那条路，
去查 BASE 的档案、查不到，打成 `<ERR BASE.地址>`。**已修好并量过**（提交 `0623c35`）。

### 14.1 决定性证据（都不用跑游戏）
- `MaterielMenu_LOAD::menuDraw()`（`DQIV_NATIVE` 分支）在正文之后**无条件**多画一行 Settings，
  把 `s_settingsEntry`（函数内 `static char[48]`，`MaterielMenu_LOAD.cpp:97`）以
  `param = (int)s_settingsEntry` 交给 `unkfunc_02050ee0`。
- `llvm-dwarfdump --name=s_settingsEntry` 打 **`DW_OP_addr 0x17bb10`** = **1,555,216**，
  和屏上的 `<ERR BASE.1555216>` 逐位相同。旧值 1,555,120 = 0x17bab0，两次构建差 **0x60 = 96 字节**
  （静态区随构建挪），正好对上交接里记的"号会动 96"。
- 判定点：`unkfunc_02050900` 的 `value` 要么是指针、要么是 id，指针判定走
  `pc::isGameTextPointer()`。它先查游戏堆分配表，Windows 再用 `VirtualQuery` 认模块数据；
  **非 Windows 分支原来直接 `return false`**（注释说"4 字节指针时整个地址空间都归游戏"——
  这只对游戏堆成立，对 `.data`/`.bss` 不成立）。
- 于是 0x17bb10 被当 id：type=0 → 提升成 `0x10000000`(BASE) → `extract_text_msg(1555216)`
  → 块 1555000 → 档案最远只到 1010000 → 失败 → `<ERR BASE.1555216>`。

### 14.2 运行时量到的
- 探针（每个模糊值打一次）：整轮（标题、菜单、新游戏）里**"可能是指针也可能是 id"的值只有 1 个**：
  `0x17bb30 -> pointer (heap base 0x1920d0)`。所以这条边界不会误伤别的 id。
- 修完：**第 4 行读作 `Settings`**（截图 `/tmp/menu-after-fix.png`）；journal 里
  `text probe` 只有 `COMM ok 406/407/408`，**没有任何 BASE 失败行**。

### 14.3 这推翻了交接里的哪几条（逐条，都是量出来的）
- **§1「整个文本系统跑在一个没有数据的空壳上」——错，撤。** 运行时 `text probe COMM ok
  406/407/408`；`<ERR>` 只出现在第 4 行（PC 版自己加的那一行）。
- **§4.5 / §5「`NAME:` 结果仍是 0 ⇒ 游戏从没按名字加载过任何东西」——错，撤。** 本轮 journal 里
  `NAME:` 有几百行（`data/G2D/FONT/zen12.nftr`、`data/map/ev01.lz`、`data/common.tex`……），
  `read()` 一直在被调用。
- **§4.7「`unk80c=0` ⇒ 档案持有者是空的」——错。** `unk_80c` 是**上一次查找的结果**，探针正好在
  一次失败之后读它，所以它当然是 0；这不是"从没装载过"的证据。
- **§4.6「block 6 的 first=1004000/last=1004503/count=82 也算池子内容」——错。** 那是 ROM 里
  `data/MESS/en/b1004000.mpt` 的**真头部**（离线解析逐字节吻合：first=1004000、last=1004503、
  count=82）。`count` 会动的只有**没被查过**的块（池子里的旧内容）。
- **§6 唯一那条押注（第 4 行 = 多出来的存档槽、全 0xFF 被判成"有存档"）——死了。** `resume_`
  只决定正文画 3 行还是 4 行；Settings 那行是 `DQIV_NATIVE` 分支无条件画的，和存档、
  和那个号都无关。真机 3 行也正因为 DS 没有 Settings 这一项。
- **§4.12「号会动 ⇒ 是数据/参数来的」——半对**：确实不是代码常量，但它是**静态缓冲的地址**，
  随构建布局挪，不随存档数据挪。

### 14.4 修法（`0623c35` + 后一条，只在 wasm 生效）
`isGameTextPointer()` 新增 `#elif defined(__EMSCRIPTEN__)` 分支，认两个区间：
1. **模块数据**：wasm32 的静态区和 `.bss` 正好止于链接器的 `__heap_base`，所以
   `0x10000 <= value < &__heap_base` 按指针算。消息 id 不会那么高。
2. **栈**：`--stack-first` 把栈放在线性内存最底下 `[0, 0x10000)`，用
   `emscripten_stack_get_end()`/`get_base()` 精确取这段。这一条是**量到才补的**：存档槽那屏
   三个数字画成了 `<ERI`（被裁掉的 `<ERR`），journal 里 `text probe BASE fail no=62720`，
   而 62720 = 0xF500 正是栈地址——`unkfunc_02050c70` 把数字 `sprintf` 进**局部缓冲**再交给
   `unkfunc_02050900`，于是"数字"也走了指针那条路。补上栈之后：存档槽读作 `1: / 2: / 3:`，
   journal **一个 BASE 失败都没有**。

**Windows 分支一个字没动**（仍用 `VirtualQuery`，它本来就把"活动调用帧里的栈字节"算进去），
所以 CI 的 Windows 作业仍是裁判：`0623c35` 那次 selfcheck / wasm / windows **三个都绿**。

### 14.5 名字/存档那屏（用户说的"字母表是 ERR 这类字符"）——已量到同一个根因
- 存档槽行原读作 `<ERI … : Unused`：左边那个是**被裁掉的 `<ERR BASE.62720>`**，来自
  `unkfunc_02050c70` 的栈缓冲（见 14.4 第 2 条）。补上栈区间后读作 `1: / 2: / 3:`。
- 字母表本身（`MaterielMenu_NameEdit::unkfunc_0203b0f0`）也是同一个形状：要么
  `*label = (int)&data_020f1c2c[pos]`（静态缓冲、第 1 条已覆盖），要么 `*label = 字符码`
  （小整数，仍然会被当 id）。**这一支没单独量**——如果还有 `ERR`，先看它是这两支里的哪一支。

## 15. 本轮（同一会话后半）：音频破音的根因，和 fps 的预算

### 15.1 根因：不是混音质量，是**欠载**（量出来的）
每一帧写 800 帧（16.67ms@48k）→ 音频产量**跟着帧率走**：
- RAF 28-40 → 实际产量 **24-31k 帧/s**，而声卡要 **48000**；
- 队列探针（`AudioOutput::write` 前读 `queuedFrames`）：**`starved 30/60, min 6`** ——
  一半的写入到达时队列不足一帧，最低只剩 **6 帧（0.12ms）**。
所以"低帧就破音"是 underrun，和混音/限幅器无关。

### 15.2 修法（`132b714`）
按**队列**补，不按帧补：每次泵把设备队列顶到 **2880 帧（60ms）**；泵点 = 帧边界 **+ 帧末**，
因为帧边界实测只跑 **13-21 次/s**，而帧是 25-40 次/s。
实测后：**`low 0/60`**，每次写入前最低 **1610 帧（33ms）**，队列再没见底。
桌面路径保持原样（800/帧，60Hz 自洽），只有 wasm 分支按队列补。

### 15.3 fps：预算是多少（headless + swiftshader，别当 Metal）
- 整帧 `step-all` = **12.9ms**，其中 `frame`(nativeStep) 12.8、`render-callback` 11.8；
- render 内部：**capture+display 5.7**（display-compose 2.6、readNative-sync 1.4、
  display-read 1.0、capture 0.6）、**present 3.5**（present-compose **3.4** = 4 个 plane 的
  字节序转换 + 2.9MB 上传）、**render3D 2.6**（field 里 6-9）。
- **对照实验**：一个空白 640×817 WebGL 画布，**带同样的 2.9MB/帧 TexSubImage2D**，headless 仍是
  **60.1 RAF**。所以 RAF 掉到 25-40 既不是"浏览器合成"也不是"上传带宽"，是**场景的 GPU 工作量**
  （headless 走软件渲染；前台 Metal 上便宜得多）。
- 结论：headless 的 RAF 不能判 60fps，要看前台真 GPU 的 overlay。我们自己的 CPU 是 12.9ms/帧，
  60fps 的余量只有 3.8ms。

### 15.4 已经削掉的，和下一步的杠杆
1. **`present-compose` 3.2-3.4ms → 1.2-1.3ms（做了）**：那是每帧 4 个 256×704 plane 的
   `0xAARRGGBB → RGBA` 转换 + 上传。原来的写法是 `assign` 一份 2.9MB 的拷贝（每次调用还新建
   vector）再逐像素用四次抽取重写；改成**复用一块 thread_local 缓冲、直接融合成一次遍历**，
   并且用掩码换 R/B（`(p&0xFF00FF00)|((p&0xFF)<<16)|((p>>16)&0xFF)`）。
   映射逐位不变：`dqiv_layout_probe.js` 的 round trip 仍是 `0x7f3a5c6e -> 0x7f6e5c3a -> ok`。
   顺带 `frame` 从 12.5-19ms 掉到 11.1-15.5ms、`render-callback` 从 11.5-18 到 10.1-14.5。
   headless 的 RAF 仍在 31-43（软件渲染的 GPU 侧瓶颈没动），所以这条在 Metal 上的收益是
   **CPU 预算少 ~2ms/帧**，不是 RAF 数字。
2. `display-compose` **2.6ms**（还没做）：纯 CPU 的 2D 合成（每屏 49152 像素 × 5 层 + 窗口/混合）。
3. `readNative-sync` **1.4ms**（还没做）：每帧一次 `glReadPixels` 同步。
