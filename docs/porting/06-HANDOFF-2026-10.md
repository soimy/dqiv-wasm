## 14. 本轮追加（同一份交接、同一天的第二段会话）：`<ERR BASE.n>` 的根因

**一句话**：那个号不是消息 id，是**我们自己 PC 菜单里一个字符串缓冲的地址**。wasm 上
`isGameTextPointer()` 只认游戏堆里的指针，模块静态区不算，于是字符串走了"消息 id"那条路，
去查 BASE 的档案、查不到，打成 `<ERR BASE.地址>`。**已修好并量过**（提交 `0623c35`）。

### 14.1 决定性证据（都不用跑游戏）
- `MaterielMenu_LOAD::menuDraw()`（`DQIV_NATIVE` 分支）在正文之后**无条件**多画一行 Settings，
  把 `s_settingsEntry`（函数内 `static char[48]`，`MaterielMenu_LOAD.cpp:97`）以
  `param = (int)s_settingsEntry` 交给 `unkfunc_02050ee0`。
- `llvm-dwarfdump --name=s_settingsEntry` 打 **`DW_OP_addr 0x17bb10`** = **1,555,216**，
  和屏上的 `<ERR BASE.1555216>` 逐位相同。旧值 1,555,120 = 0x17bab0，两次构建差 **0x60 = 96 字节**
  （静态区随构建挪），正好对上交接里记的"号会动 96"。
- 判定点：`unkfunc_02050900` 的 `value` 要么是指针、要么是 id，指针判定走
  `pc::isGameTextPointer()`。它先查游戏堆分配表，Windows 再用 `VirtualQuery` 认模块数据；
  **非 Windows 分支原来直接 `return false`**（注释说"4 字节指针时整个地址空间都归游戏"——
  这只对游戏堆成立，对 `.data`/`.bss` 不成立）。
- 于是 0x17bb10 被当 id：type=0 → 提升成 `0x10000000`(BASE) → `extract_text_msg(1555216)`
  → 块 1555000 → 档案最远只到 1010000 → 失败 → `<ERR BASE.1555216>`。

### 14.2 运行时量到的
- 探针（每个模糊值打一次）：整轮（标题、菜单、新游戏）里**"可能是指针也可能是 id"的值只有 1 个**：
  `0x17bb30 -> pointer (heap base 0x1920d0)`。所以这条边界不会误伤别的 id。
- 修完：**第 4 行读作 `Settings`**（截图 `/tmp/menu-after-fix.png`）；journal 里
  `text probe` 只有 `COMM ok 406/407/408`，**没有任何 BASE 失败行**。

### 14.3 这推翻了交接里的哪几条（逐条，都是量出来的）
- **§1「整个文本系统跑在一个没有数据的空壳上」——错，撤。** 运行时 `text probe COMM ok
  406/407/408`；`<ERR>` 只出现在第 4 行（PC 版自己加的那一行）。
- **§4.5 / §5「`NAME:` 结果仍是 0 ⇒ 游戏从没按名字加载过任何东西」——错，撤。** 本轮 journal 里
  `NAME:` 有几百行（`data/G2D/FONT/zen12.nftr`、`data/map/ev01.lz`、`data/common.tex`……），
  `read()` 一直在被调用。
- **§4.7「`unk80c=0` ⇒ 档案持有者是空的」——错。** `unk_80c` 是**上一次查找的结果**，探针正好在
  一次失败之后读它，所以它当然是 0；这不是"从没装载过"的证据。
- **§4.6「block 6 的 first=1004000/last=1004503/count=82 也算池子内容」——错。** 那是 ROM 里
  `data/MESS/en/b1004000.mpt` 的**真头部**（离线解析逐字节吻合：first=1004000、last=1004503、
  count=82）。`count` 会动的只有**没被查过**的块（池子里的旧内容）。
- **§6 唯一那条押注（第 4 行 = 多出来的存档槽、全 0xFF 被判成"有存档"）——死了。** `resume_`
  只决定正文画 3 行还是 4 行；Settings 那行是 `DQIV_NATIVE` 分支无条件画的，和存档、
  和那个号都无关。真机 3 行也正因为 DS 没有 Settings 这一项。
- **§4.12「号会动 ⇒ 是数据/参数来的」——半对**：确实不是代码常量，但它是**静态缓冲的地址**，
  随构建布局挪，不随存档数据挪。

### 14.4 修法（`0623c35` + 后一条，只在 wasm 生效）
`isGameTextPointer()` 新增 `#elif defined(__EMSCRIPTEN__)` 分支，认两个区间：
1. **模块数据**：wasm32 的静态区和 `.bss` 正好止于链接器的 `__heap_base`，所以
   `0x10000 <= value < &__heap_base` 按指针算。消息 id 不会那么高。
2. **栈**：`--stack-first` 把栈放在线性内存最底下 `[0, 0x10000)`，用
   `emscripten_stack_get_end()`/`get_base()` 精确取这段。这一条是**量到才补的**：存档槽那屏
   三个数字画成了 `<ERI`（被裁掉的 `<ERR`），journal 里 `text probe BASE fail no=62720`，
   而 62720 = 0xF500 正是栈地址——`unkfunc_02050c70` 把数字 `sprintf` 进**局部缓冲**再交给
   `unkfunc_02050900`，于是"数字"也走了指针那条路。补上栈之后：存档槽读作 `1: / 2: / 3:`，
   journal **一个 BASE 失败都没有**。

**Windows 分支一个字没动**（仍用 `VirtualQuery`，它本来就把"活动调用帧里的栈字节"算进去），
所以 CI 的 Windows 作业仍是裁判：`0623c35` 那次 selfcheck / wasm / windows **三个都绿**。

### 14.5 名字/存档那屏（用户说的"字母表是 ERR 这类字符"）——已量到同一个根因
- 存档槽行原读作 `<ERI … : Unused`：左边那个是**被裁掉的 `<ERR BASE.62720>`**，来自
  `unkfunc_02050c70` 的栈缓冲（见 14.4 第 2 条）。补上栈区间后读作 `1: / 2: / 3:`。
- 字母表本身（`MaterielMenu_NameEdit::unkfunc_0203b0f0`）也是同一个形状：要么
  `*label = (int)&data_020f1c2c[pos]`（静态缓冲、第 1 条已覆盖），要么 `*label = 字符码`
  （小整数，仍然会被当 id）。**这一支没单独量**——如果还有 `ERR`，先看它是这两支里的哪一支。

## 15. 本轮（同一会话后半）：音频破音的根因，和 fps 的预算

### 15.1 根因：不是混音质量，是**欠载**（量出来的）
每一帧写 800 帧（16.67ms@48k）→ 音频产量**跟着帧率走**：
- RAF 28-40 → 实际产量 **24-31k 帧/s**，而声卡要 **48000**；
- 队列探针（`AudioOutput::write` 前读 `queuedFrames`）：**`starved 30/60, min 6`** ——
  一半的写入到达时队列不足一帧，最低只剩 **6 帧（0.12ms）**。
所以"低帧就破音"是 underrun，和混音/限幅器无关。

### 15.2 修法（`132b714`）
按**队列**补，不按帧补：每次泵把设备队列顶到 **2880 帧（60ms）**；泵点 = 帧边界 **+ 帧末**，
因为帧边界实测只跑 **13-21 次/s**，而帧是 25-40 次/s。
实测后：**`low 0/60`**，每次写入前最低 **1610 帧（33ms）**，队列再没见底。
桌面路径保持原样（800/帧，60Hz 自洽），只有 wasm 分支按队列补。

### 15.3 fps：预算是多少（headless + swiftshader，别当 Metal）
- 整帧 `step-all` = **12.9ms**，其中 `frame`(nativeStep) 12.8、`render-callback` 11.8；
- render 内部：**capture+display 5.7**（display-compose 2.6、readNative-sync 1.4、
  display-read 1.0、capture 0.6）、**present 3.5**（present-compose **3.4** = 4 个 plane 的
  字节序转换 + 2.9MB 上传）、**render3D 2.6**（field 里 6-9）。
- **对照实验**：一个空白 640×817 WebGL 画布，**带同样的 2.9MB/帧 TexSubImage2D**，headless 仍是
  **60.1 RAF**。所以 RAF 掉到 25-40 既不是"浏览器合成"也不是"上传带宽"，是**场景的 GPU 工作量**
  （headless 走软件渲染；前台 Metal 上便宜得多）。
- 结论：headless 的 RAF 不能判 60fps，要看前台真 GPU 的 overlay。我们自己的 CPU 是 12.9ms/帧，
  60fps 的余量只有 3.8ms。

### 15.4 已经削掉的，和下一步的杠杆
1. **`present-compose` 3.2-3.4ms → 1.2-1.3ms（做了）**：那是每帧 4 个 256×704 plane 的
   `0xAARRGGBB → RGBA` 转换 + 上传。原来的写法是 `assign` 一份 2.9MB 的拷贝（每次调用还新建
   vector）再逐像素用四次抽取重写；改成**复用一块 thread_local 缓冲、直接融合成一次遍历**，
   并且用掩码换 R/B（`(p&0xFF00FF00)|((p&0xFF)<<16)|((p>>16)&0xFF)`）。
   映射逐位不变：`dqiv_layout_probe.js` 的 round trip 仍是 `0x7f3a5c6e -> 0x7f6e5c3a -> ok`。
   顺带 `frame` 从 12.5-19ms 掉到 11.1-15.5ms、`render-callback` 从 11.5-18 到 10.1-14.5。
   headless 的 RAF 仍在 31-43（软件渲染的 GPU 侧瓶颈没动），所以这条在 Metal 上的收益是
   **CPU 预算少 ~2ms/帧**，不是 RAF 数字。
2. `display-compose` **2.6ms**（还没做）：纯 CPU 的 2D 合成（每屏 49152 像素 × 5 层 + 窗口/混合）。
3. `readNative-sync` **1.4ms**（还没做）：每帧一次 `glReadPixels` 同步。

### 15.5 浏览器里"关 vsync"会把主循环踢出 RAF（用户当场撞到）
设置面板里关掉 vsync → `SDL_GL_SetSwapInterval(0)` → EGL 的 `eglSwapInterval(0)` →
`_emscripten_set_main_loop_timing(EM_TIMING_SETTIMEOUT, 0)` → 主循环改由 **setTimeout** 驱动，
控制台打出：
`Looks like you are rendering without using requestAnimationFrame for the main loop...`
后果不只是警告：帧调度脱离 vsync/RAF，实测就是掉帧。
**修法**：wasm 上忽略这个设置，永远 `SDL_GL_SetSwapInterval(1)`（浏览器的呈现是合成器的事，
"关 vsync"在页面里没有可关的东西）。桌面分支原样保留。

### 15.7 最差那处城镇（第一章）的定标：离 60 只差一个 vsync
```
RAF 29 Hz | game 30 steps/s
f 16887  cap 6647  dc 2587  dr 1057  r3d 6577  prep 2977  tex 0  pres 1280
```
周期 34.5ms = **正好两个 vsync**，我们的工作 16.9ms。16.9 + 合成 > 16.7 →
错过下一个 vsync → 33.3ms 一帧。**这是悬崖效应，不是线性变慢**：只要把工作压到
**12.7-14ms**（留 ~2-4ms 给合成），就会翻回 60，不需要砍 6ms。

下一轮的三刀（按收益/风险排）：
1. `prep` **2977**：这个循环里每个三角形把顶点块**复制三次**（`grown`、`snapped`，再
   `grown=snapped`），然后 `Prepared`（~300B）再 copy 进 vector、最后又 copy 进
   `vertices`。改成写一遍。目标 −1.2ms。
2. readback **~1.5**：`readNative` 在 wasm 上 `immediate=true`（同步 `glReadPixels`），
   改成 `FenceSync` + PBO + `GetBufferSubData` 的真异步（晚一帧取回）。目标 −1.2ms。
3. `dc` **2587**：2D 合成逐像素。目标 −0.5ms。
另有一个白捡的：`present()` 每帧都跑，但游戏只有 31 次/秒真的换帧（44 次回调）——
没换帧时跳过 present，省掉 ~13 次/秒的 2.9MB 上传。

### 15.8 第 2 条（readback 异步）在这套 Emscripten 上做不了
`native/GlLoader.hpp` 里早有结论，我复核了：**`glGetBufferSubData` 在 Emscripten 的
GL 库里没有实现**，`glMapBufferRange` 带 `MAP_READ` 会被直接拒绝
（"access does not support MAP_READ"）。所以 WebGL2 上**没有**把 PBO 读回 CPU 的路，
`readNative` 的 `immediate=true` 不是偷懒，是没有读侧。要绕开这个同步，只能改架构：
把 2D 合成也搬到 GPU（3D 层直接当纹理采样），那是另一件事，不是优化。

### 15.11 Windows 端为什么能跑高帧率（同一份渲染代码，差在四条）
1. **异步读回（PBO + `MapBufferRange`）** —— `GpuRenderer::readNative` 的桌面路径是两缓冲
   流水线：本帧 `ReadPixels` 进 PBO 就返回，下一帧再 `MapBufferRange` 取上一帧的结果，
   读的时候 GPU 早已画完，**读回不产生等待**。wasm 这条路被 Emscripten 堵死（拒绝
   `MAP_READ`、没有 `glGetBufferSubData`，见 `GlLoader.hpp`），只能同步读。真机实测：
   关掉 readback 36 → 47fps，就是这一条的价钱。
2. **没有 Asyncify** —— wasm 用 `-sASYNCIFY=1`，每个可能暂停的函数都有插桩，整程序变慢；
   原生没有。我们靠它才能 `emscripten_sleep`（60fps cap、等待）。
3. **原生 CPU** —— 同一份 C++，wasm 约 1.5-2.5× 慢（`prep` 2.0ms，原生约 0.8-1.0ms）。
4. **呈现路径** —— 都是上传 4 个 256×704 的 plane（2.9MB），桌面走驱动直接指针，
   wasm 要经 wasm 堆 → JS → WebGL 的拷贝。

**>60 的来源是插值，不是游戏跑得更快**：`GameWindow::interpolating()` 在目标 >60 且显示器
刷新 >61 时，由 `pace()` 在两个游戏帧之间插画额外帧（alpha 插值），游戏逻辑仍是 60Hz。
pacing 也不同：原生 `SDL_DelayPrecise(deadline-now)` 精确睡到 deadline；wasm 是
`emscripten_set_main_loop` 一个 rAF 一步，再叠一层 `emscripten_sleep` 的 60fps cap。

**要在浏览器里追平，缺的就是第 1 条**；WebGL2 没有把 PBO 读回 CPU 的路，替代方案只能是
"不读"——3D 层留在 GPU 上参与合成，即 A/B 里的 B 方案。

### 15.12 性能之外还没做的（按"用户能不能感觉到"排序）
1. **存档持久化（最大缺口）** —— `wasm/src/port-stubs.cpp:37` 的 `saveDirectory()` 是 `/saves`，
   在 **MEMFS** 里：**刷新页面 = 存档全丢**，而且页面只提供 F10 下载 `journal.txt`，
   **没有导出 `.sav` 的入口**。修法两条，第一条就够：
   - 挂 IDBFS（Emscripten 自带）。注意 `wasm/index.html:82` 那句注释把因果说反了——
     **IDBFS 不需要 COOP/COEP**，那是 `SharedArrayBuffer`（多线程）的要求，而我们是单线程协作调度；
   - 再加"导出/导入存档"按钮（下载/上传 `.sav`），零依赖、也是玩家的逃生通道。
2. **ROM 免重选** —— 现在每次刷新都要重新挑 ROM（`window.Module.preRun` 写 `/pack`）。
   可把 ROM 存进 IndexedDB，或用 File System Access 的句柄授权一次。
3. **输入** —— 手柄（Gamepad API）、**触摸屏**（下屏触摸映射）、移动端软键盘（起名界面）。
   这三件没做之前，手机上不能完整游玩。
4. **平台层收尾（M8）** —— `port-stubs.cpp` 的 SaveStore / NitroThreads / NitroIdentity 仍是
   naive 实现（约 55 行），`CrashHandler`、`TextCanvas`、错误弹窗还是 Windows 的。
5. **M3b** —— 真正的 overlay snapshot/restore（现在靠链接顺序 + 边界符号，够用但没做完）。
6. **杂项** —— HD 纹理包、设置界面的浏览器化、存档导出。

**性能（B / WebGPU）不在这个列表的紧急项里**：40fps 是可玩的，丢档不可接受。

### 15.13 存档持久化（IDBFS）
`/saves` 现在挂在 **IDBFS** 上：

- `wasm/index.html` 的 `preRun`：`FS.mkdir('/saves')` + `FS.mount(IDBFS)` + `FS.syncfs(true, cb)`，
  回调里调 `Module._dqiv_savesReady()`；**必须 `-lidbfs.js`**——Emscripten 4 不再默认链入 IDBFS，
  不链的话 mount 直接抛 "IDBFS is no longer included by default"（第一次就是被这个坑掉的，
  而且异常把整个 run 打断了，游戏根本没起来）。
- `native/GameBoot.cpp` 的 `main()` 开头等 `savesReady`（`emscripten_sleep(4)` 轮询，3 秒超时后
  照常启动，只是不持久化）——存档目录的读取是异步的，不能race。
- 写入后落盘：`wasm/src/port-stubs.cpp` 的 `SaveStore::write` 末尾调 `window.__syncSaves()`，
  页面里 250ms debounce 后 `FS.syncfs(false)`；另有 `pagehide` 兜底。
- **日记挪出 /saves**：`journalPath()` 在 wasm 上改成 `/tmp/journal.txt`（页面 F10 同步改）。
  否则每次存档落盘会把几 MB 的 journal 一起写进 IndexedDB。

端到端验证（headless，写 → 刷新 → 读）：`/saves` 里 `dqiv_eur.sav`（65536 字节）、
`dqiv_eur.sav.identity`、探针文件全部保留，内容一致；`/tmp/journal.txt` 2.5MB 不在 IDBFS 里。
**IDBFS 不需要 COOP/COEP**——那是 SharedArrayBuffer 的要求，之前的页面注释把因果写反了，已改。

### 15.14 ROM 免重选（IndexedDB）
挑选过的 ROM 存进 IndexedDB（`dqiv-rom` / 存 `rom` / 键 `pack`，存的是 **Blob**——结构化克隆
Blob 不会像 ArrayBuffer 那样整块复制）。之后刷新页面**自动启动**，不再弹文件选择框。

- 逃生口：`index.html?pick=1` 强制回到选择器；换一个文件会**覆盖**存的那份。
- 自动启动后 45 秒内 `window.__gameSteps` 还没出现，就把选择器放回来并提示
  "那个 ROM 没启动游戏"——避免存了个坏 ROM 之后页面永远起不来。
- 顺带调 `navigator.storage.persist()`，减少被浏览器回收的概率。

端到端验证（headless，两次访问）：第一次选文件 → `dqiv-rom:1` 里 **134,217,728 字节** →
第二次**不选文件**，`picker visible: false`、`RAF 48 / game 47`，即从存档的 ROM 直接起来了。
`?pick=1` 验证：选择器可见 ✓。

### 15.15 存档导出/导入（逃生通道）
页面右下角 `save ↓` / `save ↑`：下载 `/saves/dqiv_eur.sav`、或把一份 `.sav` 写回去并 `syncfs`。
导入后提示刷新（游戏内存里还是旧字节）。浏览器存储被清或换机器时，这是玩家唯一的备份手段。

### 15.16 输入这块其实基本已经就位（待用户实测确认）
查过代码，不需要新写：
- **手柄**：`GameWindow` 里是完整的 SDL3 gamepad 支持（`SDL_InitSubSystem(SDL_INIT_GAMEPAD)`、
  `SDL_OpenGamepad`、按键/轴、热插拔、以及改键页面 `pageGamepad`）。Emscripten 的 SDL3 走
  Gamepad API，浏览器里应当直接可用。
- **触摸**：鼠标位置已经映射到 DS 下屏坐标并调 `setTouch(down,x,y-192)`（`GameWindow.cpp:244`），
  浏览器里点下屏就是触摸；SDL3 默认还会把真实触摸事件合成为鼠标事件。
- **起名**：DQ4 用的是 DS 自带的屏幕键盘，鼠标/手指点即可，**不需要系统软键盘**。
所以"输入（手柄/触摸/软键盘）"这条待办大概率可以直接划掉，只差实测。

### 15.17 鼠标/触摸在浏览器里失效的根因（SDL 的坑）
不是坐标映射，是 **SDL3 的 Emscripten 后端把鼠标事件整体丢了**：直接调用它自己注册的
`mousedown` 处理函数（`JSEvents.eventHandlers` 里能拿到），**调用成功但没有任何 SDL 事件产生**——
它的监听注册在没有目标元素的状态下，而 SDL 要先有"鼠标焦点"才肯上报按键，那个焦点永远建立不起来。
所以点击在到达游戏之前就被丢弃。

处置（`349b4b5`）：页面接管指针事件，通过 `dqiv_pointer(down,x,y)` 直接喂给游戏
（`GameWindow::setPointer`，一旦收到过就不再依赖 `SDL_GetMouseState`），顺带覆盖真实触摸
（浏览器把触摸也发成 pointer 事件）。

链路验证：`touch: mouse 822,904 window 1433x1091 canvas 1433.0x806.1 placed 0 -> x 178.4 y 363.1 down 1`
→ `setTouch(1,178,171)` → `data_0211a5d4.touch_=1`，消费方是
`game/src/main/window/CommandWindow.cpp:159` 和 `NormalControl.cpp:170`。
**注意：城镇地图本身不吃触摸**（DS 原版也一样），触摸只在命令窗口/战斗等界面有效——
测试要点开菜单再点。

### 15.18 触摸点出来的崩溃：LCDC 源不可 CPU 访问
现象：点屏幕后报 `std::runtime_error: LCDC source bank is not CPU accessible`。

链路是通的——这个崩溃**恰好证明触摸到达了游戏**：`CommandWindow::unkfunc_0202a8fc`
的触摸分支（左上角 x<0x20,y<0x20）调 `unkfunc_020817d8()` 启动"双 3D 模糊捕获"，
随后 `unkfunc_02081814()` 用 `VIDEO_LCDC_SOURCE(0x06860000,0x8000)` 要一块 CPU 指针，
而当时那块 VRAM bank 不在 LCDC（mode 0）映射下 → `NitroVideo::lcdcSource` 抛异常。

处置：不再抛，改为**返回全零缓冲 + 一次性 stderr 提示**（`video: LCDC source ... reading zeros`）。
控制台上这种读本来也只返回总线译码到的东西；捕获因此是空白的，但游戏不会被打断。
注意 **DQ4 本身的触摸支持很有限**：菜单/地图是按键驱动，触摸只有命令窗口的角按钮等少数入口，
所以"点菜单行没反应"在原版 DS 上也是同样行为，不是移植缺陷。
